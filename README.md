# ThirdBrain — 세종시 12대 섹터 진단·공약 네트워크

「세종시 진단 12대 섹터 정리」의 **97개 진단**과 「12대 섹터 공약 브리핑 계획표」·공약자료집의
**54개 공약 과제**를 하나의 망으로 잇는다.

- 바깥 고리 = **진단(문제, ● 원)**
- 안쪽 고리 = **공약(해법, ■ 사각)**
- 선 = 어느 공약이 어느 진단을 **해소**하는가
- **공약이 하나도 닿지 않은 진단은 붉게 남는다** → 그것이 공약 공백 지점이다
- 모든 노드는 섹터 → 4대 영역 → 시(市) 라는 **수렴축**을 따라 하나의 핵심점으로 모인다

---

node server.js

## 상태 판정

| 상태 | 조건 | 색 |
|---|---|---|
| **미대응** | 겨냥한 공약이 하나도 없음 | 적색 `#d03b3b` |
| **현장 압력** | 공약은 있으나 위기 신호 1건 이상 또는 고심각 2건 이상 | 주황 `#ec835a` |
| **대응 착수** | 겨냥한 공약 1건 | 황색 `#fab219` |
| **대응 확보** | 겨냥한 공약 2건 이상 | 녹색 `#0ca30c` |

'현장 압력'을 따로 둔 이유: 공약을 냈는데도 민원이 쌓이는 지점은 공약이 아예 없는 곳과
성격이 다르다. 전자는 **설계를 고칠 곳**, 후자는 **공약을 만들 곳**이다.

### 점의 크기

```
진단 r = 6 + 1.1·√비중 + 5.2·log₁₀(1 + 신호부하) + 1.0·√대응공약수
공약 r = 7 + 1.3·√비중 + 1.7·√해소진단수 + 0.9·√공약간연결
신호부하 = Σ 심각도가중 × (1 + log₁₀(1 + 건수))
```

건수에 로그를 씌워 **한 건의 대규모 청원이 전체를 압도하지 않게** 했다.

## 색 규칙 — 왜 이렇게 정했나

**색은 하나의 일만 한다.** 12개 섹터에 12색을 쓰면 색상 식별이 무너지고,
무엇보다 **미대응 붉은색이 다른 색에 묻힌다**. 그래서 역할을 나눴다.

- **색상(hue) = 4대 영역**(12섹터를 3개씩 묶음) — 검증 통과한 4색만 사용
- **섹터 = 명도 단계 + 공간 위치 + 라벨** — 색이 아니라 위치가 섹터를 알려준다
- **모양 = 노드 종류** — 진단은 원, 공약은 사각. 색을 못 봐도 구분된다
- **붉은색 = 미대응 전용** — 섹터 색에서 적색 대역을 완전히 비웠다

4색(`#199e70` `#c98500` `#3987e5` `#ae55c1`)은 색각이상·명도대비 검증을 전 조합 통과했고
(`dataviz` 검증기), 미대응 적색 `#d03b3b` 도 네 색 모두와 분리된다.
파랑↔보라 쌍만 색각이상 경계값(ΔE 6.3)이라 라벨·공간분리·범례를 보조 수단으로 함께 둔다.

상태는 **색 + 기호(`● ▲ ◆ ■`) + 맥동**을 함께 쓴다. 모션을 끈 환경에서는 정지된 경보 링으로 대체된다.

## 데이터

```
data/
├── taxonomy.json    4대영역 · 12섹터 · 상태정의 · 연결유형
├── diagnoses.json   97개 진단  — 원자료에서 그대로 추출
├── pledges.json     54개 공약  — 브리핑 계획표 + 공약자료집
├── links.json       57개 공약 간 관계 (시너지/선후의존/상충)
└── signals.json     30건 시민 신호 — 진단에 연결
```

수렴축(진단·공약 → 섹터 → 영역 → 시)과 해소선(공약 → 진단)은 저장하지 않는다.
`resolves` 와 분류체계에서 런타임에 자동 생성된다.

### ⚠️ 원자료와 추정을 구분할 것

| 구분 | 출처 | 신뢰도 |
|---|---|---|
| 12대 섹터, 97개 진단 문구 | 「진단 12대 섹터 정리」 | **원자료 그대로** |
| 공약명·차수·목표지표 | 브리핑 계획표, 공약자료집 | **원자료 그대로** |
| **공약 → 진단 매핑(`resolves`)** | — | **추정. 검토 필요** |
| **공약 간 관계(links)** | — | **추정. 검토 필요** |
| 시민 신호 30건 | — | **예시 데이터. 실제 민원으로 교체 필요** |
| 진단 `weight`(중대도) | 미기재 | 전부 기본값 5 |

커버리지 72% 라는 숫자는 **추정 매핑에 근거한 것**이다. 매핑을 고치면 숫자가 달라진다.

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| `GET` | `/api/graph` | 분류체계·진단·공약·관계·신호 일괄 반환 |
| `POST` | `/api/signals` | 시민 신호 추가 (`title`, `targets[]`=진단ID) |
| `POST` | `/api/pledges` | 공약 추가 (`label`, `sector`, `resolves[]`) |
| `POST` | `/api/diagnoses` | 진단 추가 (`label`, `sector`) |
| `POST` | `/api/links` | 공약 간 관계 추가 |

```bash
curl -X POST http://localhost:4173/api/signals \
  -H 'Content-Type: application/json' \
  -d '{"title":"버스 배차 불만","targets":["S01-03"],"severity":"high","count":40}'
```

## 다음 단계

1. **매핑 검토** — `resolves` 를 직접 확인·수정. 여기가 이 도구의 정확도를 좌우한다
2. **진단 중대도 부여** — 97개 전부 weight 5. 우선순위를 넣으면 점 크기가 의미를 갖는다
3. **공약 보강** — 이미지 슬라이드(공약2 경제정책 발표본)는 텍스트 추출이 안 돼 미반영
4. **실제 민원 연결** — 국민신문고·새올 데이터를 신호로 투입
5. **당선 후 전환** — 공약에 실행 진척률·예산을 붙이면 그대로 시정 모니터링 도구가 된다
6. **시계열** — 분기 스냅샷을 쌓으면 망이 어떻게 변해왔는지가 보인다
7. **저장소** — JSON 파일 → DB (동시 편집 시 파일 쓰기는 안전하지 않다)
